# Native Note Sync Protocol

Every AES-256-GCM output is `nonce ‖ ciphertext ‖ tag`, with a random 12-byte nonce and a 16-byte tag.

## Keys

| Key                           | Generated by       | If leaked                                                                                 |
| ----------------------------- | ------------------ | ----------------------------------------------------------------------------------------- |
| [API key](#api-key)           | the server         | [replace it](./guides/setup-sync-server.md#connect-a-client) and enter it on every device |
| [Content key](#content-key)   | a client, at setup | never rotates, see the [threat model](./ARCHITECTURE.md#threat-model)                     |
| [Recovery key](#recovery-key) | a client, at setup | rotate it                                                                                 |

### API key

Authorizes requests. 32 random bytes from the server's CSPRNG. Serialized as 64 lowercase hex characters; parsing trims surrounding whitespace and rejects anything else. Keys derive from the 32 bytes, not the text.

### Content key

Encrypts notes. 32 random bytes, identical on every device and stored in its encrypted local database; the server holds it only under the Recovery key.

### Recovery key

Encrypts the Content key for the server. 32 random bytes, serialized as 24 words of the BIP39 English wordlist: BIP39's word mapping and checksum, never its seed derivation.

```
contentKeyEncrypted = AES-256-GCM(recoveryKey, e2eeContentKey, aad: empty)
```

A blob that opens to anything but 32 bytes does not open.

Clients never persist the Recovery key. A client puts the blob at its pinned `v + 1`, never at a fetched `v + 1`. The pin is the `v` of the last blob the client put or opened, 0 before either and again when the library [moves to an empty server](../clients/DESIGN.md#recovery-flow).

## Notes

Note store request, visible to the server:

- `blindedId` — RFC 4868's `HMAC-SHA-256-128` of the [note's UUID](./ARCHITECTURE.md#notes), as the 16 bytes [Content](#content) carries.

```
blindingKey = HKDF-SHA256(e2eeContentKey, info: "native-note/id-blind/v1", 32)
blindedId = HMAC-SHA256(blindingKey, uuid)[0..16]
```

- `v` — a `u32` starting at 1, plaintext because the server compares it. The server rejects a write unless `v == storedV + 1`, computed without wrapping: at `storedV = u32::MAX` every write is `conflict`. A client never computes `v + 1` past `u32::MAX`.
- `payload` — encrypted content. Encryption is per write, not per note.

```
writeId = 128-bit random salt, stored and transmitted in plaintext
noteKey = HKDF-SHA256(e2eeContentKey, salt: writeId, info: "native-note/note/v1", 32)
payload = AES-256-GCM(noteKey, content, aad: blindedId ‖ v_be32 ‖ writeId)
```

Content is the binary layout below.

### Content

End-to-end encrypted with the Content key, opaque to the server. Fixed binary layout, big-endian:

```
version(1) = 0x01
kind(1)
  0x01 note        uuid(16) ‖ createdAt_be64 ‖ updatedAt_be64 ‖ bodyLen_be32 ‖ body ‖ extLen_be32 ‖ ext
  0x02 tombstone   uuid(16) ‖ deletedAt_be64
fill             zero bytes up to the next multiple of 4096 B, none when the fields end on one
```

A decoder rejects a non-zero fill byte as trailing bytes whatever the length, and otherwise a length that is not the smallest multiple of 4096 B holding the fields as not canonical.

Timestamps are epoch milliseconds. `body` is UTF-8 per RFC 3629; anything else is rejected. An unknown `version` or `kind` is rejected.

Every version and kind, present and future, begins with `version ‖ kind ‖ uuid(16)`, so a client that cannot decode the rest still reads the UUID and checks the blinded ID. A client reports a change whose prefix checks out but whose `version` or `kind` it does not know as written by a newer Native Note, not as one that does not open.

`ext` is empty in this version; later versions define its content. A client keeps a note's `ext` byte for byte, writes it back with every edit, and gives a conflict copy the `ext` of the text it copies. A field a client may ignore goes in `ext`; any other change takes a new `version` or `kind`.

Deleting a note writes a tombstone. Tombstones are not garbage-collected.

## Binary encoding

Everything inside the envelope is fixed-layout binary.

Every message has exactly one valid encoding:

- Integers are unsigned big-endian at their stated width, except timestamps which are signed.
- Variable-length fields are `len_be32 ‖ bytes`. Arrays are `count_be32 ‖ item*`.
- Booleans are `0x00` or `0x01`. Any other value is rejected.
- Enum discriminants are one byte. Unknown values are rejected, except an [`error`](#response-error) `reason`, which a client reads as `fault`.
- A message must consume its buffer exactly. Trailing bytes are rejected. [Content](#content)'s zero fill is the one exception.

Decoders reject only what these rules and the per-message rules name, so a non-v4 `uuid`, a negative timestamp or a payload too short to open still decodes.

Decoders must be total: bounds-check every read, never allocate from a length or count before it has been checked against the remaining input, and return an error rather than panicking.

## Ordering

The server stamps every accepted write with a `seq`, inside the same transaction as the write, starting at 1 and strictly increasing. List ordering and date grouping are computed locally by `updatedAt`.

## Transport

The sealed envelope authenticates each request and hides its metadata. No device IDs, so an observer cannot tell devices apart or count them. TLS is optional.

A replayed write is rejected by `v == storedV + 1`, since the server has already advanced. A write that never reached the server carries no expiry, so one held back and delivered later is still accepted while its `v` is next. A replayed pull returns a response sealed to a key the attacker does not hold.

```
envelopeKey = HKDF-SHA256(apiKey, info: "native-note/envelope/v1", 32)

request  = AES-256-GCM(envelopeKey, padded, aad: empty)
response = AES-256-GCM(envelopeKey, padded, aad: requestNonce)
```

### Padding

`padded = len_be32 ‖ inner ‖ zero fill` to the smallest bucket that holds it. Buckets double from 256 B up to the [body limit](#limits), so neither request nor response length leaks more than a bucket. Unpadding rejects any other length and non-zero fill.

## API

`POST /` is the only route, and the request target is exactly `/`. Requests are HTTP/1.1 with lines ending in CRLF and one `Content-Length` of ASCII digits. The request line and headers, through the blank line that ends them, fit in 8 KiB with at most 100 headers. Other headers are ignored, and `Expect` gets no `100 Continue`. Any other method, target, version or framing is `400`, as are `Transfer-Encoding`, a header line that is folded, lacks a colon, or has whitespace before it or a name that is not a token, a CR outside a line ending, and headers past these caps. Responses carry `Content-Length` and `Connection: close`, and only `200` has a body. A client posts to its server URL as configured, so a reverse proxy may map a path prefix to `/`.

Distinct HTTP status codes exist only for outcomes with no sealed response and carry no application meaning: `400` malformed or unopenable, `413` oversize, `500` fault.

The body is the sealed envelope, parsed after GCM verification. Every sealed response is HTTP 200, and every outcome is a field inside it.

Each action is one byte; every response except `error` echoes it, and a client treats any other action as an error.

| `action` | Byte | Purpose                               |
| -------- | ---- | ------------------------------------- |
| `sync`   | 0x01 | Push writes, pull since `seq`         |
| `get`    | 0x02 | Read `contentKeyEncrypted`            |
| `put`    | 0x03 | Store or rotate `contentKeyEncrypted` |

An action's request and response layouts and the limits never change; a new layout takes a new action byte, which an older server answers with `unsupported`.

### Action `sync`

```
request    0x01 ‖ since_be64 ‖ writeCount_be32 ‖ write*
write      blindedId(16) ‖ v_be32 ‖ writeId(16) ‖ payloadLen_be32 ‖ payload

response   0x01 ‖ resultCount_be32 ‖ result*
                ‖ changeCount_be32 ‖ change*
                ‖ nextSeq_be64 ‖ more(1)
result     status(1) ‖ v_be32
change     same layout as write
```

`results` carries one entry per submitted write, in the order submitted. A client treats as an error a response with any other result count, an `accepted` result whose `v` is not the one sent, and `more` with no changes or with a `nextSeq` not above `since`, and applies none of it.

| `status`    | Byte | Description                                |
| ----------- | ---- | ------------------------------------------ |
| `accepted`  | 0x01 | Stored. `v` is the value now on the server |
| `conflict`  | 0x02 | `v != storedV + 1`                         |
| `too_large` | 0x03 | Payload over the [note limit](#limits)     |

A write that fails both checks gets `too_large`.

On every status except `accepted`, `v` is the server's current version.

The server applies a `sync`'s writes in the order submitted, then reads `changes`, so accepted writes come back in the same response. A `sync` is applied atomically: after `error` none of its writes are stored, so a retry is safe.

`changes` holds the current write of each note whose `seq` is above `since`, in `seq` order. `nextSeq` is the server's latest `seq`, or the last change's `seq` when `more` is set, and the client's next pull starts from it. A response that sets `more` carries at least one change, and the client pulls again right away.

### Actions `get` and `put`

```
get request    0x02
get response   0x02 ‖ v_be32 ‖ blobLen_be32 ‖ blob

put request    0x03 ‖ v_be32 ‖ blobLen_be32 ‖ blob
put response   0x03 ‖ status(1) ‖ v_be32
```

`v = 0` means no blob is stored, and the blob is then empty; a client treats a `get` response with `v = 0` and a blob as an error.

A `put` follows the same [version rule](#notes) as notes and answers `accepted` with the `v` sent or `conflict` with the server's current `v`; any other status in a `put` response is rejected, and a client treats an `accepted` with another `v` as an error. On `conflict` the client gets the blob. If it opens under the Recovery key the client just put, that `put` landed; otherwise [Recovery flow](../clients/DESIGN.md#recovery-flow) handles it.

### Response `error`

```
error response   0xff ‖ reason(1)
```

A request that unseals but fails to unpad or decode, or hits a fault after unsealing, gets `error`:

| `reason`      | Byte | Cause                                                                                             |
| ------------- | ---- | ------------------------------------------------------------------------------------------------- |
| `malformed`   | 0x01 | The request fails to unpad, or to decode after its action byte                                    |
| `unsupported` | 0x02 | An action the server does not know or no longer accepts                                           |
| `fault`       | 0x03 | A storage failure, a full disk, an exhausted `seq`, or a first pending change too large to answer |

A client treats an unknown `reason` as `fault`.

## HKDF label registry

New labels must not collide; a changed derivation bumps its `/v`, and a changed envelope layout bumps `native-note/envelope/v1`. `info` is the label's ASCII bytes, and a derivation shown without a salt uses RFC 5869's default of 32 zero bytes.

| Label                                          | Derives             | From                   |
| ---------------------------------------------- | ------------------- | ---------------------- |
| `native-note/envelope/v1`                      | `envelopeKey`       | API key                |
| `native-note/id-blind/v1`                      | `blindingKey`       | Content key            |
| `native-note/note/v1`                          | `noteKey` per write | Content key            |
| `native-note/localdb/v1`                       | `localDbKey`        | `argonOut ‖ machineId` |
| `native-note/machine-id/v1`                    | `machineId`         | hardware agreement     |

## Limits

| Limit                                        | Maximum | Exceeded                                                       |
| -------------------------------------------- | ------- | -------------------------------------------------------------- |
| Note `payload`, fill, nonce and tag included | 1 MiB   | `too_large` in the response                                    |
| Body, measured on [`padded`](#padding)       | 2 MiB   | Request: HTTP `413`. Response: `changes` truncated, `more` set |
